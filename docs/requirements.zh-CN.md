## 2. 用户与核心动机

用户使用 OPPO 安卓手机，骑豪爵 TVL350，主要在北京东四环辅路通勤。主辅路相邻，轨迹容易漂移，OPPO 锁屏后的定位和进程存活是实机重点。

核心问题：有时体感很堵，实际总耗时却更短。希望通过长期记录解释：今天究竟是移动更慢、等待更久，还是出发时间不同。

第一版定位为**手机独立运行的通勤记录和分析 App**。不新增车载设备，不接车辆数据，不以瞬时速度或最快纪录为主。支持真实采集和本地统计，离线仍可记录。

## 3. 已确定的范围与排除项

第一版应做：手动开始记录、后台持续定位、历史行程、由行程创建通勤路线、记录期间自动识别路线和到达、实时进度与 ETA、到达小结、月度和路线统计。

不做：独立副屏、ESP32、蓝牙设备、CAN/OBD、电源和防水硬件、海拔/山路/指南针/归途页面、信号灯倒计时、地图导航、Accessibility、MediaProjection、抓取第三方导航界面、账号登录、云同步、付费 API。

不需要等待地图平台授权。路线预览可先用本地轨迹 Canvas 实现，不能把地图 Key 或 Google Play Services 作为核心功能的启动条件。后续可扩展地图底图、导出或其他功能，第一版不要先建设这些。

“自动识别通勤路线”指**用户手动开启记录之后**自动分类，不等于 App 全天监听或自动开始记录。

## 4. 完整用户流程

1. 首次启动可看界面和空状态；开始记录时按需请求定位权限，明确说明为何需要精确位置和通知。
2. 用户点击开始，从此刻持续保存轨迹，UI 切后台或锁屏仍应继续。首次没有路线时显示普通骑行、实际耗时和等待；不要虚构进度或 ETA。
3. 第一趟可手动结束。在行程详情点击“设为通勤路线”，选择上班/下班、命名，并确认起终点范围（初版可提供简单半径和起终点摘要）。
4. 后续记录根据起点、方向及轨迹重合自动识别。刚出发可能处于“匹配中”，识别成功后整趟归类，不能把匹配前轨迹丢掉。
5. 匹配成功后显示进度、历史对比和 ETA。时间段是辅助，不应因迟出发直接拒绝匹配。
6. 进入终点范围并持续停留后结束“通勤段”，展示小结；提供手动结束兜底。区分短暂经过终点和真正到达。
7. 小结进入历史列表；可修正方向、关联路线，或标记“异常临停/绕路，不计入历史基准”。不删除原始数据来实现排除。
8. App 统计页面显示路线级、方向级和月份级汇总，重启后保留。

### 5.2 主要页面

**通勤 / 正在记录**
- 出发前：上次/常用路线摘要、“开始记录”。
- 记录中：路线/方向、定位质量、匹配中/已识别/偏离/无定位状态。

- 平均/最早/最晚出发和到达时间；平均/最快/最慢总耗时及中位数；每趟累计等待的平均/最短/最长。

## 6. 统计与算法口径

### 6.1 时间与速度

- 持久化时保存 UTC 时间戳和记录时区/本地日期依据；月度和通勤日按行程出发的本地日期归档。
- 计时优先使用单调时钟间隔，避免系统校时影响已耗时；进程/设备重启后的恢复标注数据缺口，不能把不确定间隔强算为等待。
- 总耗时 = 移动 + 静止 + 未知。位置质量或采样间隔无法判定的片段计入未知；等待比例分母明确为总耗时。
- 全程均速 = 过滤后有效距离 ÷ 总耗时；移动均速 = 移动距离 ÷ 移动耗时。缺失严重时标“数据不完整”，必要时不显示速度。
- 静止不能用 `speed == 0`。建议使用精度筛选、低速持续阈值和进入/退出滞回，阈值先集中配置并记录算法版本，实测后调整。静止确认后回溯候选区间，不能系统性漏算起始等待。
- `speed` 不可用时不要当作零；拥堵缓行不应全算为停车。停车次数来自合并后的有效静止段。
- 不承诺识别实际红灯。“静止等待”可能包含拥堵、临停；UI 与文档始终采用准确名称。

### 6.2 路线与进度

- 路线来自实际历史轨迹；起终点范围、方向、轨迹重合与有序前进共同判断。
- 进度按沿有序路线投影的距离/路线总长；不能用直线距离或总行程距离简单代替。
- 处理路线自交、平行主辅路、同起点多路线、掉头和绕路；避免最近点匹配跳到后续路段。
- 小漂移不过度倒退；真实偏离显示不确定，不为了“进度单调”掩盖绕路。到达确认后才定为 100%。
- 到达自动确认的范围和停留时长是待实测参数；UI 提供手动结束，数据模型保留可修正的通勤起止边界与原始点。

### 6.3 历史基准与 ETA

- 使用同方向、同路线、当前行程之前的有效历史，建议窗口最近 20 次；数字是建议参数，不是用户硬性要求。
- 当前行程不能参与自己的对比基准；排除未完成、异常或低质量记录。每项显示实际样本数，样本不足不输出确定结论。
- ETA 使用当前时刻 + 历史相似进度位置之后的剩余时间统计，可先使用中位数与区间，再按出发时段优化。数据少时“学习中”；无须实时路况或付费 API。
- 总耗时中位数与“移动中位数 + 等待中位数”不一定相等。解释分项时注明是分项基准，不能把两者混作同一个总基准。
- 平均出发/到达时间处理跨午夜（相对所属通勤时段展开），不要直接平均钟表分钟导致 23:50 与 00:10 得到中午。
- 月度通勤天数 = 有效通勤出发本地日期去重；单程次数 = 有效行程数；一天往返为 1 天/2 次。
- 无样本显示空状态，单样本如展示均值/最快等应说明只有一次；等待为零是合法值。

### 6.4 原型数据注意事项

HTML 使用固定示例，滑块并非真实计算模拟；ETA、进度和总时间不始终联动，统计图不是所有方向的真实聚合。截图能参考布局，**不能复制硬编码数字当生产算法**。

验证用固定例子：今天移动 `23:18`，静止 `06:18`，合计 `29:36`；历史分项移动 `22:18`，等待 `09:30`，和为 `31:48`。分项变化 `+01:00` 与 `−03:12` 合计 `−02:12`。独立的总用时历史中位数可为 `32:10`，因此总差 `−02:34`；这是两种不同基准，应清楚标注。

## 7. 建议的安卓实现（非已确定版本）

建议原生 Kotlin + Jetpack Compose，Room 本地数据库、Coroutines/Flow、ViewModel，DataStore 保存设置。优先一个 app 模块加清晰分层，不预设复杂多模块或服务器。具体 SDK、Gradle、JDK 和依赖版本在新任务查项目和本机环境后选择并固定。

- 定位接口可替换，提供真实 Android 定位实现和确定性的轨迹回放。OPPO 中国环境不要默认有 Google Play Services，优先评估系统 `LocationManager` 或不依赖 GMS 的实现。
- 用户在可见页面开始 `location` 前台服务，持续通知提供停止入口；根据 target SDK 正确处理定位、前台服务和通知权限。第一版不为全天自动开始申请无关权限。
- “锁屏持续记录”不自动等于必须申请后台位置权限。按 Android 官方权限与启动限制实现；拒绝、仅近似位置、定位关闭、权限撤回都要有明确 UI。
- OPPO 后台策略影响需真实设备测试；不能仅根据模拟器通过声称锁屏可靠。不要默认要求用户关闭全部省电保护。
- Service 是记录生命周期和状态的权威，旋转、重进页面不重复开始记录；尽快增量持久化，进程中断能找到未完成行程，重启不无声伪造采样。
- 无定位时仍计时，标记未知片段；恢复后不跨大缺口连线累计距离；拒绝明显跳点和过期点。
- 本机存储为默认；无需账号、后台服务、分析埋点或轨迹上传。日志不输出精确坐标；备份策略明确，避免系统默认备份意外上传轨迹。
- 初始 UI 中文，文案全部资源化，建议带英文资源。中英文开发文档是用户明确要求，不能只翻译标题。
- 无真实历史也应可通过单独 Demo/Replay 模式体验；演示记录不混入真实数据库统计。

参考：
- [Android 定位权限与前台记录](https://developer.android.com/develop/sensors-and-location/location/permissions)
- [运行时定位权限](https://developer.android.com/develop/sensors-and-location/location/permissions/runtime)
- [Room 本地持久化](https://developer.android.com/training/data-storage/room)

## 8. 建议数据模型

- `Ride`：ID、起止墙钟/时区、耗时依据、状态、有效距离、routeId、方向、异常排除标记/原因、质量概况、算法版本。
- `TrackPoint`：rideId、有序序号、时间/单调时钟、坐标、坐标系、位置精度、可空速度及速度精度、质量状态。
- `RideSegment`：区间边界、移动/静止/未知、距离、置信依据；保留原始点方便重算。
- `CommuteRoute`：ID、名称、方向、有序参考轨迹、起终点范围、来源行程 ID、可选常用时段、版本。
- 统计由持久化数据计算；可缓存但需能在行程归类或排除修改后重建，不只保存不可追溯的月度总数。

## 9. 开发阶段与验收

### A. 工程与真实 UI

创建可构建安卓工程；四个主页面、导航、空状态和独立 Demo 模式；把 HTML 设计转为真实 Compose。中英文 README 给出环境、构建和安装方法。不要将 HTML 直接塞 WebView 冒充原生记录 App。

### B. 真实记录闭环

权限 → 开始 → Service 定位与增量存储 → 锁屏记录 → 手动结束 → 小结/历史 → 重启仍可查看。无权限/无定位/被中断有提示；通知停止操作可用。默认不自动启动未授权记录。

### C. 通勤与统计

历史行程创建路线 → 下一趟识别 → 进度/到达/ETA → 修改归类和排除 → 月度/方向统计联动。新路线无历史时合理降级。

### 必要验证

- 有意义的算法测试：漂移静止、缓行、缺失速度/位置、大时间缺口、轨迹跳点、偏离路线、掉头、平行路/自交进度、历史不足、异常排除、跨午夜、日期去重及基准不含当前行程。
- 数据库重开、归类修改后汇总变化、服务重复启动防护；回放同一轨迹结果确定。
- 按实际工具运行构建、单元测试和关键 UI 冒烟检查，不重复无意义测试。
- 最终文档区分“已实现”“模拟验证”“待 OPPO 实测”；缺 JDK/SDK/设备时明确阻塞，不把代码写完当作已验证可运行。
- 用户自行验证：同一趟上班路线至少数次，手动计时对比静止等待、终点前短停、锁屏、地库/隧道恢复和耗电。实际准确性是后续迭代指标，不承诺精确到秒。
